# Show Me

按用户的卡点讲清楚，默认在对话中用 Markdown 回答；只讲材料能支持的内容。纯讲解任务不改被讲解材料；若用户同时要求修改，按其要求完成修改与验证，并解释相关机制和变更。修改结果按原请求的条件、相关测试或可观察行为验收，讲解不能代替修改验收。

## 选路径与深度

- **代码、diff、模块或仓库**：遇到 diff/改动前后、非确定性取值、设计理由、跨文件影响或深入讲解，读 `workflows/explain-code.md`。只有单个当前实现（非 diff）的确定性局部窄问，才可读原始材料后直接答，不加载 workflow。
- **论文或技术报告**：读 `workflows/explain-paper.md`；研究论文、研究型报告走研究骨架，设计说明、ADR、提案型 RFC、规范型 RFC/标准、事故复盘等按文档目的走非研究报告分支。只问一个结论或局部细节时聚焦该处，不展开整篇。
- **概念、术语或机制**：稳定概念的窄问可直接答；深入讲解或涉及具体系统、库、协议及版本时，读 `workflows/explain-concept.md`。
- **论文与实现对照**：加载论文与代码两个 workflow；论文链接的 release/tag/commit 是实现匹配线索，还须核对论文声明的实验版本、时间与行为，不能仅凭链接认定实验用了该版本；无法确定对应版本就标明。逐项给出“主张/公式 → 实现位置 → 一致、差异或未核验 → 证据范围”。其他混合请求若包含多个独立目标，逐项选路径并交付；只需一个结论时以最贴近卡点的类型为主，仍核对另一类材料中必要的证据。
- 深入讲解再读 `commons/plain-craft.md`，按读者背景给整体结论、心智模型、关键例子与边界；窄问直接回答，不强加图、术语表或自测。无背景线索时，代码按有编程基础但不熟本领域、论文/技术报告/概念用普通读者能理解的词汇。对象、理解目标或目标格式无法从上下文确定且会改变结论、讲解主轴或交付时才问；宽泛问题可先讲共同核心，随后按用户反馈下钻。
- 用户已明确要求深入讲解时，首轮至少讲透一条与问题最相关的机制、因果或推导链，配一个能走通的例子及适用边界；宽泛主题按所求维度连续下钻并核对覆盖清单，不能以总览、路线或等待读者追问代替已请求的深度。读者反馈用于调整讲法，不是停止条件。

## 取材与可信度

- 具体代码、论文或技术报告先读用户给的原文，或自行定位一手材料；暂不可得时，可据可回查摘要、用户片段或署名二手材料给注明来源层级的初步解释，关键结论仍需原文时再索要；没有可回查依据就索要材料。不把二手转述写成作者主张或实现事实。自行定位论文时核对题名、作者、出处或标识、版本/日期，在答复中给出可回查的链接或路径及所用版本；同名或多版本无法唯一确定时说明选择与证据，差异影响结论时再问。只取得片段或摘要，就限定结论，不补写未读的机制、实验或局限。一般概念可用已有知识解释；具体系统或库先确认相关版本并读该版本的一手文档或源码，版本差异影响答案而无法确定时再问。
- 代码行为以实现为准，不凭名称猜测；随机、时间、网络等没有运行记录时，只给可推得的条件或范围，不编确定取值。设计理由仅在原始材料明示时归于作者；实现推论标为推断并说明依据。用户只说“求证”而未指定深度时，至少核对可得一手材料的关键主张与直接证据，给出“支持/不支持/尚不能判断”及依据；效果、因果或推广主张还须查方法、对照、指标及可能的反证条件，关键材料缺失则判尚不能判断。核验整份材料时，纳入用户点名的主张、摘要/结论/建议中的可检验主张及支撑它们的关键效果或因果断言，逐项给证据状态；只把背景定义和明确无关的旁枝列为范围外，用户明确要逐条全核则全部列入覆盖清单，未覆盖项不称已完成全篇求证。仅转述或只有二手材料时不称已完成求证。独立复算或复现只在用户要求或结论离不开它时做；实际完成哪层就报告哪层，阅读原文不等于独立验证。
- 引用源文件用真实 `file:line`；仅有粘贴代码时，从片段第一行起用 `用户片段:行号`。在线材料若只提供不带稳定行号的网页文本，给可回查 URL、章节/标题与短摘录或页面锚点，注明没有稳定行号；不虚构文件、行号、版本或调用方。跨文件或长时间取证临交付前复核关键引用和所据工作区状态。论文注明已读章节、公式或图号；扫描页或图中关键证据看不清时目视/OCR 核对，仍不清楚则标未核验并索要清晰材料。
- 跨文件关系的结论若依赖共同源码状态，按 `workflows/explain-code.md` 的同状态规则取证；无法证明则把当前关系标未核验，仍可解释各文件已读到的规则与成立条件。未要求逐条全核的整份求证，还应记录未核但可检验的正文旁枝及排除理由，未读内容不称无关；明确逐条全核时，可读且可检验的断言均须入清单，不以“旁枝”排除。
- 用户明确要逐条全核时，先按页或章节建立发现清单，扫描可取得的正文、表格、图注、脚注、附录及图面中的坐标轴、图例、面板标注和可辨数据，逐项记可检验主张与出处；看不清的图面或尚未扫描的位置列为未覆盖。未完成主张枚举时不称全篇求证完成。
- 求证逐项注明判断依据与核验层级（作者报告、原始材料核对、独立复算或复现）；“支持”只在注明的层级内成立，阅读原文不称已独立核实。
- 用户说“求证这篇论文/这份报告”等指向整份材料但未说“逐条全核”时，默认核验摘要、结论、建议和支撑它们的关键可检验主张；按是否改变主要结论、适用范围或行动建议选取，给出取舍理由和未核范围。明确逐条全核时，按 `workflows/explain-paper.md` 的发现单元、拆分与完成判据枚举全部可得断言；不可读或缺失处列未覆盖，不称全篇全核完成。大材料可分阶段持续处理，不以路线或首阶段充完成。

## 回答与核对

- 有明确卡点就先答它。范围有限的宽泛问题给短总览，再讲至少一个核心机制或证据；未要求深入或完整的开放式超大主题可给分阶段路线并讲完当前一小阶段，说明未覆盖范围。用户明确要求深入、完整讲解或完整文件时，按所求维度和粒度覆盖全部范围，不把逐行穷举当作“完整”；范围巨大时列覆盖清单并分阶段连续完成，记录每阶段产物、未覆盖项及续接位置。需要跨轮或上下文续做时，将清单、已读来源、已完成项和下一入口存入工作区或宿主可持久载体；若无法保存进度，说明未完成范围而不宣称全量交付。路线与首阶段不算完成。读者说“还是没懂”时换更浅的说法、例子或纠正前一解释。
- 普通练习按用户要求给题及答案/判断依据；用户要检验自己的理解时先出少量题并等作答，再逐题判断和纠错，不在作答前泄露答案；若要立即看答案，则按普通练习处理。用户同时要先讲解时，先讲再出题。
- 交付前核对答案是否直接解除用户卡点，以及必要例子、边界、出处和未核验范围；多章节、模块或阶段任务逐项核对覆盖清单，未完成项不报完成。图文混合交付核对同一节点、关系、方向和条件是否一致；读者实际理解须看其反馈或作答，不凭作者自检宣称。不能把“如代码/公式所示”当成解释。深入讲解可按需给一项后续下钻方向，简短回答不附工作汇报。

## 交付形态

- 对话内的 ASCII/Mermaid 辅助小图仍属普通讲解；网页里的辅助图也不触发 Archify。用户明确要**独立可交互**的架构、时序、流程、数据流或状态图时，读内置 `archify/SKILL.md`，按其 `finalize`、真实浏览器 `basic-interaction-smoke --all-viewports`、必要的视觉检查交付，任何必需门槛失败只交草稿。独立交互图优先于一般 HTML 排版。Archify 环境不可用，或其 Git 收据无法证明非 Git、无可用 origin/commit、未提交工作区等目标源码字节时，读 `references/interactive-alternative.md`，制作前预检能力，具备时按替代路径从来源到最终文件重新验收；不得把 HEAD 当工作区证据。Archify 内容或可读性门槛失败时先按诊断修复；仍失败可另制新文件走完整替代验收，不沿用失败收据或暗降门槛。两路径都无法完成验收时只交草稿并说明缺口。Archify 工作、HTML 和证据目录须在支持交付锁的真实本地文件系统；完整校验需 Node ≥18 与 Chrome/Chromium，Windows 可用 Edge 回退。内置 Archify 不是可直接调用的独立 skill。
- Show Me 路由的 Archify 独立图还须对最终文件运行 `visual-check --summary --require-provenance`，亲自目视其截图/联系表，并补看未覆盖的实际布局、用户指定视口及纵向滚动后首屏外的卡片/图内容；检查主路径、关系方向、标签与控件是否一眼可辨，修复后重跑受影响的完整验收。截图生成不等于目视通过，无法目视或发现未修复的可读性问题只交草稿；单独使用 Archify 的普通生成仍按其自身可选视觉复核规则。
- 若五类图只是 Archify 的 Git 收据不能证明非 Git、无可用 origin/commit 或未提交源码字节，但其布局/浏览器工具可运行，可在**替代路径**中借用 Archify 生成 HTML：候选同时省略 `meta.repository` 与节点 `sources`，在外部独立记录实际来源；不把 `finalize` 或 `--require-provenance` 收据称为源码核验。仍按替代路径独立核对实际源码、跨文件状态、语义、交互、目视和用户可取得副本。Archify 质量门槛失败仍须修复，不能改称替代图就接受同一失败文件；渲染器不可用或图型不符时再选其他工具。
- Archify 基础 smoke 默认要求至少一条实际关系；无边默认失败。只有用户目标明确要求零关系，或来源与范围证据证明不应有交互、流向、依赖或状态迁移时，才在 `--all-viewports` 上加 `--expected-no-relationships`：核对全图确实零边，并在真实浏览器验节点激活、匹配详情、可见空关系态和返回全图；收据的关系反馈为“不适用”，不能写成已通过。无法证明零边合理或显式检查失败，只交草稿。
- 其他独立可交互图型（如概念关系图）不套用 Archify 的五类 schema；先读 `references/interactive-alternative.md` 并做制作前能力检查，具备时按其来源、内容、文件和交互门槛制作，失败按该路径修复或留作草稿。通用文件/HTML 编辑加浏览器可算候选能力，仍须能打开最终本地文件、控制视口、实际操作交互、检查运行时错误并目视；缺项直接交草稿，说明缺口。
- 制作独立交互图前，把用户明确点名的全部节点、关系、条件，与从描述/源码推得且回答问题必需的角色、主路径、行为改变条件和边界，一并列成“预期 → 成图位置 → 证据或未核验”对照；宽泛请求也须先给语义覆盖基准。成图后逐项核对呈现、方向和条件，并检查全体节点/关系是否引入与来源相矛盾的含义。必需项缺失或只能靠未经标明的推断补上时，不把浏览器或布局收据当作语义验收通过。
- 独立交互图先查看 CSS/媒体查询或脚本中影响布局的断点，并在浏览器确认实际布局；四个固定尺寸不能自动证明覆盖中间断点。对每种实际布局及用户指定的每个视口操作关键详情与返回全图，并目视可读性，不能用静态视口检查代替；若含不同节点或关系交互形态，另按形态各实际操作一个，报告所测与未测范围。Archify 的四个默认视口只覆盖桌面；未在手机视口实测就不声称手机适配。用户要求手机可用时，还要在该视口实际滚动找到节点、展开可能折叠的关系列表并核对展开状态与关系内容、打开详情并返回，核对内容和控件可读、可操作及无运行错误；声称触屏支持还须用触屏模拟或设备操作。基础抽验不称逐节点验收。
- 独立交互图无论走 Archify 还是替代路径，制作前先确认宿主有可用的共享工作区、附件或下载通道；交付前再确认用户实际可取得最终 HTML，并核对该副本的字节数与 SHA-256 和验收文件一致。仅代理浏览器能打开远程临时文件，不证明用户可取得；无法确认时只交草稿。替代图还须目视要求的视口；源码快照仅作私有取证，含无关敏感内容的原始文件不得随图外带。
- 用户明确指定格式（如网页、单文件 HTML、Word、PPT/PPTX、图册或 PDF）时，先查当前宿主的对应工具/技能并交付该格式；仍缺能力才说明阻碍，素材或大纲仅称草稿。指定格式无法承载所要的独立浏览器交互时，先确定用户更重视格式还是交互，或分别交付两份，不暗称单文件兼具。不把 HTML 冒充其他格式，不因“发我一份”自动上传或发布；只要口头解释时不生成额外交付文件，长任务可存内部进度检查点；用户明确禁止写文件则不写。格式不明且无法从上下文推断时再问。
