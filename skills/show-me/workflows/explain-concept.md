# explain-concept — 把知识点讲直白

对象：一个概念 / 术语 / 机制 / 原理（没有具体源码或论文，或用户只想懂"它是什么"）。目标：读者建立**正确的直觉**；有易混概念时能区分它们。

用户只问一个定义或区别时，直接回答并按需给一个最小例子，不必读 `../commons/plain-craft.md`；要系统理解概念时，先读该文件，再使用下面的骨架。

## 深入讲解骨架

### 1. 一句话锚

先用**读者已有词汇**说它解决什么问题，或帮助解释什么现象；必要时一句话给出暂时的直觉，精确定义放在动机之后。若必须用术语，同句解释。

> 有合适类比时：它就像 <已知事物>：<一句话说明>。

### 2. 为什么需要这个概念，再给定义

人为设计的工具或机制，可从"没有它会怎样"讲起；自然现象或描述性原理，则说明不用这个概念时，相关现象如何描述、解释或预测，以及这个概念补足了什么。不要暗示现象本身可以不存在。再据此说明概念的准确含义。

### 3. 类比（适用时）与边界

- 有不失真的好类比时，用**最多一个**主类比建立直觉，并说明它在哪儿失效
- 没有好类比时，直接用下一节的具体例子或可观察案例，不硬造类比

### 4. 最小例子或可观察案例

能手工推演时，选最小例子，写清条件、过程和结果；数字只在有助于理解时使用。描述性或观察型概念可用可观察案例或一手材料佐证：

- 说明观察到什么、支持什么结论，以及适用边界
- 无法手算时说清证据来自观察或材料，不把观察写成演算

### 5. 机制 / 结构（分层）

- 关系复杂时用一张对话内关系图或流程图辅助，不为此生成独立 HTML
- 关键组成/性质逐条：**是什么 → 为什么/有何作用 → 适用边界**；人为设计的方案再说明代价

### 6. 常见误解

| 错误直觉 | 正确直觉 | 为什么容易错 |
|----------|----------|--------------|
| `<误解>` | `<正解>` | `<成因>` |

### 7. 与易混概念的关系（需要时）

- 存在影响本次理解的易混概念时，说明区别（一句话对照）；没有就跳过
- 在更大体系中的位置（可选，看用户需要）

### 8. 术语表与按需自测

- 对新术语给回查解释。普通练习可给少量边界或"若去掉某个前提会怎样"的问题及答案/判据；用户要检验理解时先只出题、等作答，再逐题判断、指出误解并针对性纠正，未作答不称检验完成

## 概念场景专属规则

| 规则 | 说明 |
|------|------|
| 动机先于定义 | 不从教科书定义开篇；先说它解决的问题或帮助解释的现象 |
| 类比按需，最多一个 | 有合适类比才用，并说明失效边界；没有则用具体例子或可观察案例 |
| 例子或证据可核对 | 可推演时写清条件与结果；观察型概念用案例或一手材料，不强求数值或手算 |
| 按需划清易混概念 | 只对照会影响本次理解的概念；没有易混点时不扩展 |
| 涉及真实系统时读一手 | 讲某库/某协议的行为，去读官方文档或源码，不转述二手 |
| 不确定就标注 | 有争议或版本差异的地方明确说明 |
