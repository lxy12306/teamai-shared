# Gen Skill

按任务范围交付可复用的 skill，并分别确认文件结构、目标宿主的发现与真实任务行为。让说明改变实际决策；不要把通用写作偏好当成所有 skill 的格式要求。

## 确定任务与位置

1. 判断本次是新建、局部改进、触发问题、拆分还是合并，并按用户目标确定交付到文件草稿、宿主发现，还是实际父路由可用。写清目标用户与任务、典型输入、必达行为、已知失败及约束；从用户请求、现有 skill、失败记录或项目材料中取证，缺少真实案例时标明推断。复杂或高错误代价的任务列出每项核心目标与约束，验收时逐项找可观察证据。任务中断后先检查已写文件并从实际进度续接，不重新初始化。能从上下文推断的内容直接采用。只有用途、必达行为或验收结果、目标宿主、必要权限或目标位置确实无法确定且会改变结果时才询问。
2. 查找同名或相邻能力的 skill。按目标、触发场景、输入输出和维护归属比较：重合时采用或改造现有实现，确有独立用途时才新建；迭代时先定位实际源文件和安装或同步链路，避免只改一份副本。用户要求外部调研时，核对候选的源码、许可证、适用宿主和可复用机制，在隔离位置阅读候选，不为比较而覆盖现有 skill。
3. 用户指定路径优先；迭代时沿用已确认的源位置。新建且只需生成时，先查目标宿主已配置的技能扫描根，再在扫描范围外的工作区或系统临时目录准备草稿；验证后移到用户指定或工作区稳定的交付位置，仍是草稿则明示其状态。明确要求安装、同步或项目约定直接交付时才写入相应目标位置。不要默认所有宿主都使用当前仓库的 `skills/`。名称与目录一致，采用目标宿主支持的字符规则；为不同宿主共享时，以共同可用的字段和资源布局为基线。

## 总 skill 与子 skill 路由

用户明确指定总 skill 路由独立子 skill 时按此结构交付；未指定时，若一组场景需要共同入口和明确选择规则，且子流程能被单独请求、调用和维护，也采用分层结构。只供总入口内部调用的条件分支放 `references/` 或 `workflows/`。确定结构前，逐个核对目标宿主能否发现独立子 skill、父入口能否读取或调用它、能否确认实际来源；无法实测时保留父子源码结构，把该宿主的父路由标为待验证。子 skill 的目录名及 `name` 必须采用 `父skill名-场景名`，例如 `suite-a`；定名时核对目标宿主的字符与长度限制，父名要给子名留出长度。用户固定的父名使子名超限时，不擅自缩名，报告冲突并请用户选择合规名称。跨 Codex、Qoder、Pi 时将它们作为**同级、独立的 skill 目录**，分别交付；不要假设嵌在总 skill 内的子 `SKILL.md` 会被三者同时发现。

```text
skills/
  suite/SKILL.md       # 总入口：判断场景并路由
  suite-a/SKILL.md     # 子 skill：场景 A 的完整流程
  suite-b/SKILL.md     # 子 skill：场景 B 的完整流程
```

- 总入口的 `description` 概括整套能力的宽泛、组合及各子任务场景，给缺失子 skill 时被选中留机会，同时避免与各子 skill 的具体描述完全重复。正文用“任务信号 → 职责与预期结果 → 子 skill 名称 → 预期来源 → 交付时状态”的路由表；该状态只是快照，调用时先按宿主已发现信息轻量核对。仅在能确认技能清单和目标文件未变时复用会话内的核对结果；来源不明、无法确认是否变更或发布更新后再查扫描根。预期来源标明套件或团队身份，不写跨宿主固定路径。准备发布的套件在路由表和每个子 skill 正文记录相同的套件修订标识，交付前逐个比对；不把它写成未经核实的通用元信息字段。按用户要的结果与职责边界选一个主子 skill；多个场景都命中但只需一个结果时选最贴合者，无法区分就澄清。请求确实跨越多个职责时，选出所有必需的子 skill；总入口写明输入输出交接、依赖顺序及结果冲突的处理规则，不限制为两个。
- 总入口被调用后，先确认请求匹配哪个子 skill；没有匹配项时说明路由表未覆盖，不硬选，含糊时澄清。按名称及预期来源核实目标子 skill 在当前宿主可用，再加载其 `SKILL.md` 并执行；宿主列表不给路径时，从已配置的扫描根中找到唯一且修订相符的副本再读取。不能只提到名称就当作完成调用。缺失、未实现、来源不符或无法确认唯一副本时，停止盲选并报告具体障碍，不能凭总入口猜出子流程；名称唯一但 Agent 无法读取时提供该宿主的显式调用方式，重名时先消除冲突。若宿主既不让总入口读取子文件，也没有已验证的调用机制，仅声称子 skill 可直调，不声称父路由在该宿主可用。自动选用取决于宿主，不能承诺总入口必然兜底；交付时提供可明确调用总入口的方式，并按交付范围测试缺失场景。
- 每个子 skill 有自己的 `name`、可区分的 `description`、完整执行步骤及其私有资源；它也能被用户直接使用。总入口不复制子流程，子 skill 不依赖先读取总入口。同名 skill 出现在多个来源时，先盘点目标宿主的可发现目录；能看到实际加载信息时核对路径、来源及修订，不能确定唯一来源时消除冲突或标为未验证，不按名称盲选。拆分、合并或重命名父 skill 后同步更新所有 `父名-场景名` 子 skill 的目录、`name`、路由表、描述、链接和交付清单；先迁移已知调用者，能保留自有旧入口时安排兼容。无法兼容旧名时，按破坏性变更记录未知调用者可能中断；只有完成已知调用迁移与约定兼容期，才按退役计划清理旧入口，不把未知调用者当作已排除。
- 只在总入口内部复用、无需独立发现的内容放到 `references/` 或 `workflows/`，由总入口写明读取条件与跳过条件；各 workflow 应能独立说明本场景的执行主体。它们不是子 skill。只有多个流程实际共享内容时才抽出公共资源；子 skill 直调所需的资源须随该子 skill 交付，或放在目标宿主可访问且已验证的公共位置并显式引用，不能隐式依赖总入口的私有目录。不要把“读参考文件”和“路由到独立 skill”混为一谈。
- 发布或安装整套能力时把总入口与所有子 skill 列成同一发布清单，逐个交付并核对名称、修订、目标副本及回退依据；在任务指定的每个宿主可发现位置检查总入口与子 skill，跨 Codex、Qoder、Pi 交付时检查三者。即使 Pi 能递归发现，仍用同级布局保证三者兼容；不要假定同步工具推送总入口时会自动包含同级子 skill，也不要假定分项派送对各宿主原子生效。采用分层路由或跨宿主交付时读取 [Codex、Qoder、Pi 路由与发现](references/cross-host-routing.md)。

## 设计与编写

- `SKILL.md` 必须有目标宿主可识别的 YAML 元信息，至少包含 `name` 和 `description`。描述用简短的“能做什么、何时使用”区分相邻请求；只有容易误触发时才写排除边界。不要用长触发词清单代替适用条件。
- 主文件写目的、关键判断、必要步骤、真实约束和按需资源入口。假设 Agent 已有一般能力，删去常识、重复规则、空泛提醒和未经证实的例外。具体程度与错误代价相称：开放任务写结果与判断标准，脆弱或高风险操作写清顺序、校验及停止条件。
- 简单 skill 保持单文件；复杂度和独立调用需求决定是否采用上面的分层路由。只有条件性材料确有用途时才加入 `references/`；在入口写明何时读取对应文件。重复或一次性但规模大、易出错的确定性操作适合 `scripts/`，例如数值汇总、正则/ID 关联、XML/JSON 解析与编码转换；新增或修改后实际运行。产出所需模板等放 `assets/`。不要因行数或章节模板机械拆分，也不要创建空目录、占位文件或项目未要求的辅助文档。
- 以目标宿主的实际规范和验证器为准。不要把某一宿主的扩展字段、执行器、审批流程或安装路径写成通用要求；需要多宿主兼容时分别核实差异。保留现有可用的 UI 元数据、调用策略和依赖字段；不兼容时把宿主专属配置放在各自支持的附属文件或部署副本中，保持共享流程一致。
- 迭代时先记录症状和可观察的旧行为，再做最小改动。先排除宿主未发现或未加载、权限不足、外部工具不可用等非 skill 文本原因；确认加载正常后，漏用或误用检查描述与能力边界，调用正确但执行出错检查工作流、资源和脚本。合并两个独立 skill 前列出各自对外行为、调用者及冲突规则，明确保留、迁移或停止的部分；拆分或合并后检查相邻描述、链接与安装入口，避免残留冲突。若目标已有 `evolution-log.md` 或项目要求变更留痕，按既有格式更新；不强制新建日志。已有用户授权的常规编辑直接完成，不因目录结构变化设置固定确认点。

## 验证与交付

1. 运行目标宿主可用的结构验证器，并检查文件名、元信息、相对链接、脚本路径和未完成占位内容。Codex 环境可使用内置 `skill-creator/scripts/quick_validate.py`；Windows 控制台若有编码问题，用 `python -X utf8` 运行。结构通过只表示格式可加载。
2. 运行新增或改动过的脚本。用代表性请求检查 skill 是否被正确选中、是否遵守关键判断，以及最终操作或产物是否达标；新建或明显改动流程并以可复用能力交付时，再用同类任务的不同输入检查流程能否重复适用。分层路由先逐个验证子 skill 的 `父名-场景名`、目录与元信息一致；能在隔离环境加载目标宿主时，再验证各子 skill 在仅安装自身时可直调，以及父入口的各路由分支、跨职责组合、缺失子 skill 的处理及重名时的来源。明确区分总入口已被调用后的缺失处理与自动选用总入口的能力。新建复杂 skill、明显改动工作流、修复触发问题或处理行为回归时，读取 [评测与迭代](references/evaluation.md)；小修只复测受影响的行为。
3. 修复已观察到的失败并针对失败案例复测。分别报告源码与结构已完成、目标宿主已发现、真实任务行为已验证到哪一步；若交付范围包含安装或团队同步，核对全套目标副本与实际加载版本。首次安装、父路由规则或发现布局改变时，在每个可操作的目标宿主对路由表的各子 skill 分别运行父入口路由请求及子 skill 直接调用；支持跨职责组合时再运行代表性组合请求。只改子流程时复测受影响分支及相邻、组合回归，未测试的分支或组合标为未验证。无法操作宿主、尚未安装或来源仍有冲突时标为相应行为未验证；如果用户要求宿主可用性，明确该项验收尚未完成、阻碍及后续验证条件，不把静态校验写成宿主可用，不以自检表代替执行证据。
