# 评测与迭代

在新建复杂 skill、大幅修改工作流、修复触发或已发现行为回归时使用。按错误代价选择测试规模；普通小改无需搭建完整评测框架。

## 准备案例

- 优先从用户实际请求、已知失败、项目任务或执行记录中挑少量代表性案例；若没有实例，根据已知用途和输入资料推导并标明“推导案例”，不要称其为真实请求。写清可观察的成功条件：是否选中 skill、关键决策、实际操作和最终产物。断言行为，不断言固定标题或措辞。
- 复杂或高错误代价的 skill，把每项核心目标与约束对应到至少一个案例及可观察结果；一条案例可覆盖多项，无法覆盖的项目单列为未验证。普通小改只需覆盖受影响的目标，不为映射创建固定表格或案例数量。
- 新建或明显改动流程并以可复用能力交付时，选同类任务的不同输入运行相同流程，检查关键决策和产物是否仍满足成功条件；只对已测输入与环境作结论。
- 检查触发时包含明确请求和不说出 skill 名称的自然请求；再选容易混淆但不该触发的近邻请求。边界问题只在真实混淆处测试。
- 修复漏触发或误触发前记下失败请求、预期选用与实际选用；修后至少让原失败请求及相关近邻请求符合预期，并把结论限制在已测请求与宿主，不用一次成功概括为稳定触发。
- 迭代已有 skill 时保留旧版和失败请求作为对照。可行时在同一任务上分别试旧版与新版，比较产物和执行记录；不要只比较文本长短。
- 涉及外部系统、费用或生产数据时使用隔离工作区、模拟数据或只读检查，并遵守原任务的授权边界。

## 执行与改进

1. 能在隔离环境加载目标 skill 时，实际运行案例；有独立执行环境时优先让评测者只看请求、skill 和必要原始材料，不预先透露期望答案或拟修补点。无法加载时可由评测者按 `SKILL.md` 的步骤人工演练并审阅产物，但这只检查流程文本和产物，不能证明宿主触发、加载或路由；把这些行为标为未验证。
2. 同时看触发、步骤、工具或脚本调用、产物。结构验证与行为验证分开记录；验证器无法证明实际任务成功，单次案例成功也只证明已运行的输入与环境。
3. 根据失败原因做局部修改，再运行失败案例和邻近回归案例。反复出现同一种确定性手工转换时，可考虑固化为脚本并测试脚本。
4. 高投入场景可扩展案例集、基线与留出测试集，防止只优化已知提示词。不要把固定案例数、重复次数、盲评界面或某一宿主专属命令设为所有 skill 的交付门槛。
