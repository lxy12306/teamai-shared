# S4 · to-tickets（拆本地工单）

把已确认的 spec、共识或用户明确需求拆成有验收价值的本地工单。可直接从已有输入进入；工单不是实现计划，也不会自动发布到 GitHub Issues。格式见 [工单格式](../references/ticket-format.md)。

## 切分与依赖

- 优先按用户可观察的端到端能力切竖片，而不是机械按前端、后端和数据库分层；纯基础设施/迁移工作若本身有独立验收价值，也可单列，不强凑用户界面。
- 第一张尽量打通最薄主链路；后续工单可显式依赖尚待完成的前序工单，只要前置完成后本单可单独实施、审查和验收。记录依赖及哪些工单可并行，禁止依赖环。
- 每张工单有稳定编号、目标、范围、验收与来源（spec 的 `R` ID，或明确需求/共识的具体条目）。沿用项目目录及编号约定；默认 `{TICKET_DIR}/NNNN-<slug>.md`，新增序号取最大值加一，落盘前重查冲突。

## 执行与核对

1. 读本次已确认范围，排除尚未裁定且会阻塞验收的部分；明确排除且有依据的待定范围不阻碍剩余工单。若输入是 `draft`，只把其中已有有效确认依据的条目纳入可执行工单。
2. 先列工单及需求覆盖关系，再写文件。只有粒度选择会明显改变交付边界时才问；用户已要求拆工单就直接完成，不固定暂停等待清单确认。
3. 做双向检查：本次范围的每条已确认需求至少被一张工单覆盖（有 R ID 用 ID，否则引用原文的具体条目）；每张工单都能找到来源且有完成判据。检查重复、遗漏、相互矛盾、依赖环和术语漂移；发现问题先修正或如实列出受阻项。

若用户还要求实现计划，继续 S5，以 spec/明确需求为来源，工单仅作切分与依赖参考；单独请求 S4 时交付文件路径、覆盖结果和未决范围后收尾。
