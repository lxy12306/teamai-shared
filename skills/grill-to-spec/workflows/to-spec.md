# S3 · to-spec（转规格）

把用户已给出的需求、已确认决策、项目现有契约与可核验约束整理为可评审的 spec。S1 共识文件不是硬前置；用户直接提供明确需求时就从这里开始。默认写到项目约定位置，否则 `{SPEC_DIR}/<slug>.md`，格式见 [spec 格式](../references/spec-format.md)。

## 执行

1. 读完整输入及相关现有文档，分清现状、目标、非目标和验收。改造既有项目时，先看本次功能相关的实现与测试，核实当前行为；查不到就标为未知，不写“目前没有该能力”或“纯新增”。每条要写入 spec 的要求至少有一个可回查来源：用户原话/确认结论、现有契约、标准或查证过的代码事实；记录可定位的消息、文件位置或版本，无法取得永久定位时保留简短引文与日期并标明限制。现有行为只有在用户要求保留时才自动成为目标约束。
2. 给本次功能和非功能硬需求稳定 ID（`R1`、`R2`……）；修订既有 spec 时保留已有 ID，停用的 ID 不改派给新需求。写出可观察行为、边界/失败场景和验收。非功能要求只有确有来源时写可测值或明确判据；不凭常识补数字，纯背景事实不必编号。
3. 对会改变本次范围、行为、权限/数据或验收的未知项定向澄清。用户要求先出草稿时，将未定点编为 Q ID，写明影响的 R ID、是否阻塞和下一步，保持 `draft`；不把未确认选择伪装成要求。验收样例未列某边界输入，不代表通用 R 已排除它；若该边界会改变实现或验收，先查项目契约与目标语言语义，再按证据定状态，不能自行缩窄范围。可逆低影响假设写明依据，供审阅。
4. 按用户已授权的交付直接写文档，增量编辑既有文件并保留无关内容。只有范围结构确有多种会影响结果的选择时才先请用户决定，不把“大纲确认”作为固定暂停点。有权主体明确确认本次行为和验收，或适用且已生效的契约明确覆盖本次要求，且无阻塞项时才标 `agreed`；记录依据，不用文件存在代替批准。定状态前逐项对照 Q 与受影响的 R/验收：若写着“实现前须裁定”且属于本次范围，就标阻塞并保持 `draft`；除非能指出有依据的范围排除。

## 核对

- 逐项核对 ID → 来源 → 行为 → 验收；没有来源的扩项删去或标作待裁定建议。
- 术语与项目权威文件和目标语言一致，只写本次确需解释的概念，不搬入其他语言的边界值；目标与已核实的当前行为的差异、迁移影响有明确记录；无实现代码级细节。
- 明示本次未覆盖、仍待定和可继续的范围。用户还要求工单或计划时，按已授权范围继续 S4/S5，不要求再确认一次阶段推进。
