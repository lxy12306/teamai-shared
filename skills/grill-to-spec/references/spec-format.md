# spec 格式

沿用项目现有 spec 位置；没有约定时落 `docs/specs/<slug>.md`。目标：一个零上下文的人读完能明白「要建什么、为什么、边界在哪」，但**不含实现代码级细节**。

## 模板

```md
# <方案名> Spec

> 状态：draft | agreed   ·   来源：<本次输入/确认结论/有效契约的定位>   ·   确认：<有权主体及答复定位，或适用契约条款；draft 写待确认>   ·   日期：YYYY-MM-DD

## 背景与目标
{为什么做这件事；解决什么问题；成功长什么样。}

## 范围
- **做**：<纳入范围的能力>
- **不做**：<明确排除的，防止范围蔓延>

## 术语
复用项目权威术语文件；此处仅列本 spec 高频且需强调的术语。

## 需求 / 行为
按能力分组，为每条稳定编号并注明可回查来源：

- **R1 <需求标题>**
  - 行为：<期望行为>
  - 验收：<Given/When/Then 或判据>
  - 来源：<类型 + 可回查定位：会话消息与短引文、文档路径/章节/版本，或契约条款/生效版本>

## 约束与非功能需求
性能、安全、合规、兼容性等。凡属本次必须交付的约束，同样给稳定 R 编号、可回查来源和可观察的验收判据，纳入工单/计划覆盖；只作背景的已查证事实可不编号。不要凭常识编造阈值。

## 当前与目标的差异
<修改既有系统时写经相关实现或测试核实的当前行为、目标行为及必要的兼容/迁移影响；无法核实时标未知，不把未查证写成不存在；纯新项目可省略>

## 待定与开放问题
- Q1 · <未定事项>；影响：<R 编号或范围外>；阻塞本次交付：是/否；下一步：<查证或用户裁定>
```

## 规则

- 每条需求有可回查来源：用户直接要求、已确认决策、现有契约/规范，或用户明确要保留的已核实行为。来源同时记可取得的定位：会话链接/消息定位与必要的脱敏短引文、文件路径与章节/版本，或契约名称、生效版本及条款；无永久消息定位时保留日期、主题和必要的脱敏短引文并注明限制，不编造 ID。敏感上下文优先记安全的内部定位，不复制无关原文。不能把所有需求硬改写成“决策”；无来源的新增内容须删去或标成待裁定建议。修订时保留既有 R 编号，停用编号不复用。
- 用项目权威术语文件中的规范词；无术语文件时保持文内一致。只收本次范围需要的术语，按目标语言和技术栈解释，不混入无关语言的边界值。
- 不下沉到实现（不写具体类名、函数签名、SQL）；实现细节属于 S5 `to-plan`。
- 所有未定项（包括成文中新发现的问题）统一列入“待定与开放问题”，注明影响的 R 编号、是否阻塞及下一步；本次要求仍受阻时保持 `draft`。若 Q 影响本次 R/验收且写“实现前须裁定”，不得同时标“阻塞：否”或将整份 spec 标 `agreed`；样例未覆盖不算范围排除，只有可回查的明确排除依据才可列为非阻塞。`agreed` 须有用户或经确认有权裁定的负责人对本次行为和验收的明确确认；若以契约为依据，须核实它已生效、适用于本次范围，且明确规定本次行为和验收。记录确认主体、权限依据或契约条款及定位；仅有文件或未批准草稿不算确认。
- S5 可直接消费已确认 spec，不要求先拆工单；未解决的待定项不能冒充可执行需求。
