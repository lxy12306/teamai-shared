# ADR 格式

沿用项目现有 ADR 位置与编号；没有约定时存放于 `docs/adr/`，顺序编号 `NNNN-<slug>.md`（如 `0001-<slug>.md`、`0002-<slug>.md`……）。懒创建目录，第一条 ADR 需要时才建。

## 模板

```md
# {决策的简短标题}

> 状态：proposed | accepted · 来源：<有权主体的裁定及可定位依据，或可回查的设计结论>

{1-3 句：背景是什么、决定了什么、为什么。}
```

保持简短，但状态与来源不可省：`accepted` 表示有权裁定者已确认的取舍，尚待确认或仅为建议时用 `proposed`。来源写具体答复或文档位置，不把文件存在当作确认。

## 可选区段（仅当确有价值时加，多数 ADR 不需要）

- **后续状态**（`deprecated | superseded by ADR-NNNN`）——决定退役或被替代时记录
- **Considered Options**——仅当被否决的备选值得记住
- **Consequences**——仅当有不明显的下游影响需要点出

## 何时写 ADR

优先记录长期影响架构、外部契约或团队协作，且理由不易从代码看出的真实取舍。下面三项是筛选线索，而非要求用户为每条决策都填满的表单：

1. **改变代价**：逆转困难，或迁移与兼容代价可观。
2. **上下文价值**：未来读者缺少背景会误解这项决定。
3. **真实权衡**：存在值得记录的备选及具体取舍。

普通可逆细节、显然的做法或无真备选通常跳过；用户明确要求记录的决策按其范围处理。访谈发生在非目标工作树时先给文件就绪提案，确认目标位置后再写入。

## 符合条件的典型

- **架构形态**：「用 monorepo」「写模型事件溯源，读模型投影进 Postgres」
- **上下文间集成模式**：「Ordering 与 Billing 走领域事件，不走同步 HTTP」
- **带锁定的技术选型**：数据库、消息总线、鉴权、部署目标（不是每个库，只是换掉要花一个季度的那种）
- **边界与范围决策**：「Customer 数据归 Customer 上下文所有，其他上下文只按 ID 引用」——明确的「不做」和「做」一样有价值
- **刻意偏离显而易见路径**：「用手写 SQL 而非 ORM，因为 X」——防止下个工程师去「修」一个刻意为之的设计
- **代码里看不见的约束**：「因合规不能用 AWS」「响应必须 <200ms，因合作方 API 契约」
- **非显然的否决**：考虑过 GraphQL 但因微妙原因选了 REST → 记下来，否则半年后有人再提 GraphQL
